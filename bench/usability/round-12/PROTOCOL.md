# Round 12: four ways to give agents a post-mortem trace (protocol)

Written before any run. Changes after the first run are listed at the end.

## Question

Rounds 7–11 gave agents a trace of a failing run that can't be replayed, but each round changed
how. Across rounds, having the trace mattered more than the way it was accessed; the comparisons
were across different days, setups and prompts. Round 12 runs the four conditions side by side, on
the same day, with the same prompt apart from one paragraph:
- **A:** no trace;
- **Q:** the trace with pmdb's query language;
- **P:** the trace with pmdb's Python library;
- **F:** the trace with only its binary format's specification.

It asks how success and cost compare.

## Methodology

### The exercises and how they were selected

The exercises are post-mortems: a production job produced wrong figures, and the run can't be
replayed because its input or state is gone. They were not sourced from real incidents. They were
designed and written by Claude in this study, for the following reasons:
- **Earlier exercise sources didn't need runtime evidence.**
  - Mechanical mutants of small and larger programs (rounds 1–3) were localized by reading. A
    reading-only screen found all 18 of round 3's candidates.
  - Real bugs mined from GitHub (rounds 4–5) were localized from their failing tests or were
    unsolvable from the issue text.
- **Round 6 built six scenarios needing runtime evidence.** Only the post-mortem one separated
  agents with a trace from agents without.
- **Round 7 generalized it** into five post-mortems with different reasons the run can't be
  replayed: private input, changed external state, the clock, a consumed queue.

Round 12 uses the three of round 7's five (`../round-7/scenarios/`, unchanged) on which agents
with pmdb did worst in rounds 7–9:

| exercise | why the run can't be replayed | the reported symptom |
|---|---|---|
| card-ledger-queue | the card processor's queue messages were consumed | debits €808.30 short of the bank, on 202 cards |
| payroll-postmortem | the private HR export was deleted after payment | salaries €16,904.43 above HR's preview |
| refund-postmortem | the payment provider's webhook export never leaves production | NovaPay refunds €5,027.67 (+42%) too high |

Each exercise contains:
- a program of about 1,000–1,100 lines in a dozen or more modules (`work/`);
- the production log and the report of the failing run;
- an issue written as a user's report, stating the figures and why the input can't be shared.

The private input is generated by a seeded generator, along with hidden variants. A validation
script checks that:
- the symptom reproduces;
- the reference fix passes the oracle;
- plausible wrong fixes fail it;
- recording the trace changes nothing else.

### The bugs

Each exercise has one planted bug. In every one, the code is correct for the common case, and a
data condition present only in some records makes it compute wrong totals silently. Nothing
crashes, the program's own checks pass, and the triggering data exists only in the lost input,
which the trace preserves.

| exercise | type of bug | mechanism | triggering records |
|---|---|---|---|
| card-ledger-queue | incomplete identity key | the re-send fingerprint omits `network_ref`; offline clearings (transit, tolls) have no auth code and a date-only time, so distinct same-day fares collide and are dropped as re-sends | 280 clearings on 202 cards |
| payroll-postmortem | unchecked invariant on intervals | employment is taken as (first row's start, last row's end), so gaps between contract rows count as employed days; salary, allowances and contribution ceilings are affected | 9 of about 650 persons |
| refund-postmortem | data-model drift after an upstream API change | a new API sends one event per status change of a refund (pending → succeeded/failed) under the same id; each event is booked as a refund | 103 of 354 NovaPay refunds (multi-event or still pending) |

**Fixes:**
- **card-ledger:** add `network_ref` to the fingerprint, one line.
- **payroll:** make employment respect each row's end, in the shared employment helpers.
- **refund:** keep each refund's last event, and count it only if it succeeded.

**What makes them hard to find by reading:**
- the faulty code looks deliberate (documented conventions and docstrings);
- the deciding condition is only in the data;
- each exercise has decoys (parking of out-of-order clearings, a proration divisor, pending
  refunds);
- the logs show only totals.

### What each arm gets

Every arm gets the same prompt: the issue, one paragraph about tools, the instruction to fix the
root cause with a minimal change, and a closing `RESULT:` line. Only the tools paragraph differs.
- **A (no pmdb):** "Python 3 is installed, including pdb." No trace.
- **Q (query language):**
  - **In the prompt:** "pmdb … is installed, and a trace of the run … has been recorded. Use pmdb
    and this trace", followed by the query language's reference
    ([harness/query_reference.txt](harness/query_reference.txt), 347 words).
  - **Installed:** `/opt/pmdb/bin/pmdb` only.
- **P (Python library):**
  - **In the prompt:** "pmdb's Python library … is installed, and a trace … has been recorded.
    Use the library and this trace", followed by the library's reference
    ([harness/python_reference.txt](harness/python_reference.txt), 339 words).
  - **Installed:** the package `recorder` on `PYTHONPATH`.
- **F (format specification):**
  - **In the prompt:** "A trace … has been recorded; no tool to read it is installed, so write
    your own reader if you need one. Use this trace", followed by the format's specification
    ([harness/format_reference.txt](harness/format_reference.txt), 358 words).
  - **Installed:** nothing.

**Common to the trace arms (Q, P, F):**
- They are required to use the trace; whether agents would choose it isn't measured.
- They get the same automatically recorded trace, `/work/report.pmdb`. It is recorded per run in
  the sandbox by `pmdb-record` (`sys.monitoring`) with the recorder at `659d619`
  (unchanged since `9003d9d`). Arm Q's `pmdb` was built from the sources at `ebc8a19`. It holds every call of the
  program's own code, with arguments by parameter name and outcomes, in format 1.1 with the value
  table.
- No arm gets a skill, and none annotates functions by hand.
- The references are always in the prompt, so no agent has to discover the documentation.

**The environment** is the same for every run:
- **Agent:** Claude Code headless, with Bash, Read, Edit, Write, Grep and Glob.
- **Sandbox:** bubblewrap, no network, the API only through a relay, and this repository's store
  copies hidden.
- **Workspace:** `/work` holds the program, the log, the report and, in Q/P/F, the trace.
- **Limits:** 80 turns and 24 minutes per run.

### How we measure

**Design:**
- 4 arms × 3 exercises × 3 models (Haiku 4.5, Sonnet 5, Opus 5.5) × 1 repetition: 36 runs.
- The plan is drawn with seed 12, then sorted to start Haiku first, then Sonnet, then Opus (the
  longest runs first).
- Up to 24 runs at a time, so the round finishes in about 30 minutes.

**Success:** the exercise's oracle runs the final sources in the sandbox on hidden inputs plus the
original case, and passes only if every figure is right. Partial fixes fail, e.g. excluding
pending refunds, or patching only the salary function.

**Cost:**
- tokens (input, cache creation, cache reads and output), summed over all result events of the
  session, or over its API responses if it timed out;
- tool calls and turns;
- wall time.

**Behaviour:** for each run, from the transcript:
- pmdb commands and failed ones (Q);
- `recorder` scripts (P);
- the reader written and its fixes (F);
- `export` use.

**Analysis:** descriptive.
- Each run's success, tokens and tool calls, per exercise and model.
- Totals per arm and model.
- Arms A and Q/P/F of rounds 9–11 as references for variance.

With one run per cell, differences of one or two successes are within noise. The round is meant to
compare the four conditions under identical conditions, not to estimate effects precisely.

### Threats to validity

- **The exercises are hand-designed by the model family under evaluation** and designed to need
  runtime evidence. They show where a trace helps, not how often real bugs are like this. Their
  decoys and naming may suit Claude.
- **Few exercises (3), one bug each, and one run per cell.** Per-exercise quirks and run-to-run
  variance (large for Haiku) weigh heavily.
- **The trace arms are required to use the trace,** which charges its overhead even where reading
  would do. The no-trace arm A never sees the decisive data, so it can only win by reading.
- **The references differ in content.** The query language and the Python library are summaries
  of larger interfaces; the format is complete. Agents with the library or `export` can also do
  their analysis in Python.
- **The 24-minute limit** may cut a few long Haiku or Sonnet runs that the 30-minute limit of
  earlier rounds allowed (the longest earlier run took 23.4 minutes).
- **Running 24 at a time** may slow runs and hit rate limits. An interrupted run is redone, not
  counted, which could extend the round.
- **No feedback questionnaire,** so no self-reported difficulties, to keep within the time
  budget.
- **The sandbox's leaks were checked.** The store copies of the repository are hidden. The
  recorder and `pmdb-record` are mounted only while recording. Only arm P can import `recorder`,
  and only arm Q has `pmdb`.
